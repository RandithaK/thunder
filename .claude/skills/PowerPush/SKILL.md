Orchestrate the PowerPush PR preparation workflow interactively, step by step, using git commands and user confirmations.

---

## Pre-flight Checks

Run all checks before proceeding. Abort early with a clear explanation if any fail.

1. **Check current branch**
   ```bash
   git rev-parse --abbrev-ref HEAD
   ```
   - Abort if result is `main` or `master` — user must switch to a feature branch first.

2. **Verify remotes**
   ```bash
   git remote -v
   ```
   - Abort if `upstream` is not configured. Guide the user to add it:
     ```bash
     git remote add upstream <upstream-url>
     ```
   - Abort if `origin` is not configured.

3. **Ask for dry-run mode** using `AskUserQuestion`:
   - Question: "Enable dry-run mode? (Shows commands without executing them)"
   - If yes, print each command but skip execution for every step below.

---

## Step 0: Commit Uncommitted Changes

```bash
git status --porcelain
```

- If the output is **non-empty**: confirm with the user via `AskUserQuestion`, then run:
  ```bash
  git add .
  git commit -m "WIP: Auto-commit before squash"
  ```
- If the output is **empty**: inform the user that there are no uncommitted changes and skip this step.

---

## Step 1: Squash Local Commits

```bash
git merge-base main HEAD       # get merge base
git log <merge-base>..HEAD --oneline   # list commits since main
```

- If there is **more than 1 commit** since main:
  1. Show the commit list to the user.
  2. **Auto-generate the squash commit message**:
     - Extract all commit subjects from the commits
     - Filter out "WIP:" prefixed messages
     - Use the first meaningful commit subject as the squash message
     - If no meaningful subject exists, fallback to: "Generating a squash commit message from the commit history." {generated-message}"
  3. Display the generated message and confirm with the user via `AskUserQuestion`: "Use this squashed commit message? {generated-message}"
  4. If user approves, run:
     ```bash
     git reset --soft <merge-base>
     git commit -m "<auto-generated message>"
     ```
  5. If user rejects, use `AskUserQuestion` to get an alternative message, then proceed.
- If there is **only 1 commit**: inform the user and skip this step.

---

## Step 2: Update Main from Upstream

Confirm with the user via `AskUserQuestion`, then run:

```bash
git checkout main
git pull upstream main
git push origin main
```

After completion, inform the user that main is now in sync with upstream and the fork.

---

## Step 3: Rebase Feature Branch onto Updated Main

Confirm with the user via `AskUserQuestion`, then run:

```bash
git checkout <feature-branch>
git rebase main
```

**If a rebase conflict is detected** (non-zero exit):
- Stop and guide the user through resolution:
  1. Open conflicting files and resolve the conflicts.
  2. Stage resolved files: `git add <file>`
  3. Continue: `git rebase --continue`
- Once resolved, continue to Step 4.

---

## Step 4: Force Push Feature Branch

Confirm with the user via `AskUserQuestion` before force-pushing, then run:

```bash
git push -f origin <feature-branch>
```

---

## Completion

- **Dry-run**: Summarise all commands that would have been executed. State that no changes were made.
- **Live run**: Confirm the workflow completed successfully. Remind the user to open or update their PR on GitHub.

---

## Error Recovery Reference

| Error | Recovery |
|-------|----------|
| Rebase conflict | Resolve files → `git add .` → `git rebase --continue` |
| Push rejected | Check branch protection rules on the remote |
| Upstream not found | `git remote add upstream <url>` |
| Not a git repo | Verify `.git` directory exists in the working directory |
| Already on main/master | Switch to feature branch: `git checkout <branch>` |
